## 2. `5643cd8` "Remove compound mesh child material limit (#172)", 2026-09-25 — PORT (engine half), the layout work is the cost

**What it does.** Removes `B3_MAX_COMPOUND_MESH_MATERIALS` (4). A compound's mesh child no longer
carries four inline material slots; the baked blob gains one shared `uint16_t` material map
(`b3MeshInstance.materialOffset/materialCount`) and the accessor structs hand out a pointer into it.
The four sites that silently **clamped** a triangle's material index to 3 now assert it in range and
index the child's real map. This is the upstream half of **fixed3d#52**. The cap is replaced by a
64K ceiling on the shared table (`B3_ASSERT( materialCount <= UINT16_MAX )`).

**Is it a bug fix?** Yes, a silent-wrong-answer fix, but upstream did not see it fail first: the two
new tests (`CompoundMeshManyMaterials`, `CompoundMeshContactMaterial`) are written against the new
API and cannot even compile against the old one. The red-first test for fixed3d has to be written
here: build a mesh child with six materials, ray-cast the sixth triangle, and assert the resolved
`userMaterialId` — that assertion fails on today's tree, which clamps to slot 3
(`src/shape.c:2465`, `src/compound.c:823/910/1194`).

## 3. `f8c4fe8` "Shape cast support for box movers (#180)", 2026-10-06 — PORT, the cleanest fix of the six

**What it does.** `b3ShapeCast`'s iteration-0 handling had two branches: encroach-and-retarget when
`canEncroach && distance > 2 * linearSlop`, else "Initial overlap" → unconditional hit at the
midpoint. So a shape that starts in the band `0 < distance <= 2 * linearSlop` reports a hit at
fraction 0 **whatever direction it is sweeping** — receding, sliding or grazing. The commit inserts a
third branch for that band: keep half a slop of rest separation, consume the rest by first order, and
miss if the sweep cannot consume it.

**The same pre-image is in fixed3d verbatim.** `src/distance.c:1112`:

```
if ( input->canEncroach && distanceOutput.distance > b3FixMul( B3_FIX( 2.0f ) , linearSlop ) )
{
        target = distanceOutput.distance - linearSlop;
}
else
{
        // Initial overlap
        output.hit = true;
        ...
```

and `src/physics_world.c:3278` sets `worldContext.input.canEncroach = mover->radius > B3_FIX( 0.0f )`,
so only a positive-radius capsule mover enables encroachment at all — and that path never reaches
this block: `b3ShapeCast` measures against
`target = b3FixMax( linearSlop, totalRadius - linearSlop )` on core-to-core distance, so a
capsule's first-iteration distance is never inside the `0 < distance <= 2 * linearSlop` band. The
band is reached only by calling the public `b3ShapeCast` directly with zero radius and
`canEncroach` true, which is what the tests below do: this is box-mover support, not a live engine
bug.

**Red-first tests:** `ShapeCastEncroachRecedeTest` and `ShapeCastEncroachSlideTest` both assert
`output.hit == false` for a segment 2 mm off the box's +x face swept away from it and tangentially;
today's `else` branch returns `hit = true`, so both go red without any neutering.
`ShapeCastStartTouchingDefaultTest` (`canEncroach = false`) and `ShapeCastEncroachOverlapTest`
(genuinely overlapped) are **controls** that are green before and after — name them as controls, not
as evidence.

**Fixed-point hazards, named line by line** (quotes from `extern/fixed/include/fixed/fixed.h`):

- `float retained = 0.5f * linearSlop;` → `b3Fixed retained = linearSlop / 2;`. Integer halving is
  the idiomatic spelling and is exact-truncating; `B3_LINEAR_SLOP` is
  `b3FixMul( B3_FIX( 0.005f ), b3GetLengthUnitsPerMeter() )` (`include/box3d/constants.h:49`), raw 327
  at one unit per metre, so retained = 163 raw. Do **not** write `b3FixMul( B3_FIX( 0.5f ), slop )`:
  `fixMul` rounds half **up** (`product + FIX_HALF >> FIX_FRACTION_BITS`, fixed.h:200–220), which
  would give 164 and cost a multiply.
- `float needed = distanceOutput.distance - retained;` → plain int64 subtraction, no helper.
- `float approach = -b3Dot( delta2, distanceOutput.normal );` → unchanged shape. `b3Dot` is the
  fused raw-128 form in this tree (47d7f7c record), so the dot is full precision; keep the unary
  minus **outside** the dot rather than negating an operand — negating inside would be a
  reassociation, and reassociations are not free here.
- `if ( approach <= b3MaxFloat( needed, 0.0f ) ) return output;` → `b3FixMax( needed, 0 )`. **Port
  the `<=` exactly**: it is what makes the division below safe. `fixDiv` is quoted as
  "`if ( b == 0 ) return a > 0 ? FIX_MAX : ( a < 0 ? FIX_MIN : 0 );`" (fixed.h:224–231) — the poor
  man's infinity — so a `<` here would let `approach == 0` through and produce a saturated fraction
  that passes the `maxFraction` test as a false miss.
- `float fraction = needed > 0.0f ? needed / approach : 0.0f;` → `needed > 0 ? b3FixDiv( needed, approach ) : 0`.
  `needed > 0` must stay a bare compare, not a squared tolerance (rule 7: `FixMul(d,d) > 0` is false
  below d ≈ 0.004 and `needed` here is at most ~491 raw ≈ 0.0075). `fixDiv` **truncates toward
  zero**, so the fraction is floored — the cast hits marginally earlier than the real root, which is
  the safe direction. Magnitudes: `needed` lives in (−163, 491] raw and `approach` is a sweep length,
  so with a 1 m sweep (65536 raw) `fixDiv(164, 65536) = (164 << 16) / 65536 = 164` raw = 0.0025
  exactly, matching upstream's expectation. The 64-bit fast path applies (`|a| < 2^47`), so no
  128-bit arm and no saturation.
- `output.point = b3MulAdd( distanceOutput.pointA, input->proxyA.radius, distanceOutput.normal );`
  → unchanged; `b3MulAdd` already exists in the fixed form at the sibling site two branches down.
- No sqrt, no trig, no reciprocal-then-multiply (the form is already divide-last), no sign-of-product
  predicate, no struct layout, no recording bytes, no new public API.
- Test tolerances: `ENSURE_SMALL( output.fraction, FLT_EPSILON )` must be floored to
  `8 * B3_FIXED_EPSILON` per the test conventions; `ENSURE_SMALL( output.fraction - 0.0025f, 0.0005f )`
  is a 32-raw window on a 164-raw value, which survives but should be stated as measured;
  `ENSURE_SMALL( output.normal.x - 1.0f, 0.001f )` = 65 raw, comfortable. The 2 mm and 5 mm gaps
  (`1.002f`, `1.005f` → 131 and 327 raw) are well above the 1/65536 resolution, so the geometry is
  representable and no case collapses.

## 4. `003a3f7` "Fix recording crash on compounds (#181)", 2026-10-06 — PORT the seven lines, but the crash is unreachable here

**What it does upstream.** Upstream's compound blob had grown a **second** live pointer,
`tree.proxies`, when `f555ee4` split leaf data out of the tree nodes. `b3ConvertCompoundToBytes`
nulls both:

```
$ git show 003a3f7:src/compound.c | sed -n "/^uint8_t\* b3ConvertCompoundToBytes/,/^}/p"
uint8_t* b3ConvertCompoundToBytes( b3CompoundData* compound )
{
        // scrub these pointers before serialization
        compound->tree.nodes = NULL;
        compound->tree.proxies = NULL;
        return (uint8_t*)compound;
}
```

but `b3RecInternCompound` nulled only `tree.nodes` by hand, so interning a **live** compound during
keyframe capture hashed a replay-time `proxies` pointer. That hash never matched the seeded slot's
hash, `b3InternGeometry` appended a new entry, and
`B3_ASSERT( player->keyframeRec->registry.entries.count == regCountBefore )` in
`b3RecCaptureKeyframe` fired — in release, the keyframe referenced a geometry id past `slotCount`.
The two hunks make both sites go through `b3ConvertCompoundToBytes`, and make the seed hash the
nulled **copy** rather than `slot->bytes`.

**Why it cannot happen in fixed3d.** fixed3d's `b3DynamicTree` has no proxies array at all — leaf
`categoryBits` and `userData` live in `b3TreeNode` (`include/box3d/types.h:1713`ff: `version`,
`nodes`, `root`, `nodeCount`, `nodeCapacity`, `proxyCount`, `freeList`, `leafIndices`, `leafBoxes`,
`leafCenters`, `binIndices`, `rebuildCapacity` — no `proxies`, no `parents`, no `dfsOrdered`):

```
$ grep -rn "b3TreeProxy" include/ src/
(no output)
$ sed -n '658,664p' src/compound.c
uint8_t* b3ConvertCompoundToBytes( b3CompoundData* compound )
{
        // scrub this pointer before serialization
        compound->tree.nodes = NULL;
        return (uint8_t*)compound;
}
```

and fixed3d's `b3ConvertBytesToCompound` restores exactly that one pointer
(`src/compound.c:665`–`689`, `compound->tree.nodes = (b3TreeNode*)( (intptr_t)compound + compound->nodeOffset );`).
So the hand-rolled null in `src/recording.c:1204` (`( (b3CompoundData*)bytes )->tree.nodes = NULL;`)
and `b3ConvertCompoundToBytes` scrub the same single pointer, the two hashes agree by construction,
and the seed's `b3Hash64NonZero( slot->bytes, ... )` equals `b3Hash64NonZero( copy, ... )` because
`copy` is a fresh `memcpy` of `slot->bytes` and nothing mutates `slot->bytes`
(`src/recording_replay.c:748`: "the pristine bytes must survive for keyframe registry seeding").
